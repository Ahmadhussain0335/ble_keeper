## Failures

### F1 (withdrawn): no notifications after a peripheral service change

Recorded from O1, then reproduced under control at 11:58 (nRF Connect force-stopped while Phone A was connected): after `onServiceChanged` the plugin rediscovered and the peripheral app logged "notifications enabled" (11:58:26 Phone B clock, about 4.5 s behind Phone A). Subscribing after a service change works. In O1 the plugin had subscribed to nRF Connect's identical service (see SL2). Not a plugin failure; nothing to fix.

### F2 (minor, FIXED in b287fb1, verified in B1): `RestoredAfterKill` and "service started after boot" after a user force-stop

- Evidence: 2026-10-14/A6c-force-stop-plugin-log.txt: `note "received android.intent.action.BOOT_COMPLETED"` at 13:03:06.926, right when the user opened the force-stopped app (no reboot), followed by `blocked userForceQuit`, `note "service started after boot"`, `restoredAfterKill`.
- Root cause (hypothesis): Android 15+ sends BOOT_COMPLETED to an app when it leaves the stopped state after a force-stop. BootReceiver treats every BOOT_COMPLETED as a reboot and starts the service with ACTION_BOOT, which emits `RestoredAfterKill` and filters to `restartOnBoot` sessions.
- Impact: misleading event (the app was not restored by the OS; the user relaunched it after a force-stop) and, for sessions with `restartOnBoot: false`, they would not be resumed by this path (they still resume when the UI attaches). Connection behaviour is otherwise correct.
- Proposed fix (needs approval): in BootReceiver, distinguish a real boot from "left stopped state": e.g. compare `SystemClock.elapsedRealtime()` with a few minutes, or on API 35+ check `ActivityManager.getHistoricalProcessStartReasons` / `ApplicationStartInfo.wasForceStopped()`; when it was a force-stop relaunch, skip `RestoredAfterKill` (userForceQuit already reports it) and let the UI attach path resume all sessions.

### F3 (minor): force-stop within 60 s after an app update is not reported

- Evidence: B1 run 1. `lastUpdateTime` 13:29:37 (Phone A clock), force-stop about 13 s later, relaunch: no `blocked userForceQuit`. Run 2 (force-stop minutes after the update) reported it.
- Root cause: the verification-pass fix for spurious userForceQuit after an app update (API 30-32 record update kills as REASON_USER_REQUESTED) ignores every REASON_USER_REQUESTED exit within +-60 s of `PackageInfo.lastUpdateTime`.
- Impact: a real force-stop in the first minute after an update goes unreported (false negative). Rare in practice.
- Proposed fix (needs approval): the update kill happens at install time, so only ignore exits from about 30 s before to 5 s after `lastUpdateTime`; on API 33+ the update has its own reason (REASON_PACKAGE_UPDATED), so apply the window only below API 33. Extend ExitReasonsTest accordingly.

### E1 (example app, FIXED in bdcb1c0, verified in B1): device ID field is empty after a restart

After the process restart the example's address field was empty and `keepConnected` failed with `ArgumentError (deviceId must not be empty)` (the plugin's input check worked). Proposed fix (needs approval): prefill the field from `BleKeeper.instance.activeDeviceIds()` on start.

### D1 (documentation, FIXED in 2fea712): per-minute Data summaries are lost on a process kill

Evidence: A6b. The README "Event log and privacy" section says a process kill can lose "the newest seconds of the log"; for Data summaries it can be up to 60 s, because counts are aggregated in memory for a minute before they are written. State events are unaffected. Proposed fix (needs approval): either correct the README sentence, or flush the Data aggregator more often (for example every 10 s) at the cost of more log lines.

## Setup limitations

### SL1: peripheral address changed between S1 and the test session

- The S1 session targeted Phone B's address while nRF Connect advertised. After nRF Connect stopped, Phone B advertises from the test app with a different private address, so the S1 session can never reconnect (Android returns status 135 immediately for autoConnect to that address). This is the rotating-address limitation of a phone peripheral, not a plugin failure. Side note for the example app: it has no way to stop sessions whose ID is not in the text field (only `activeDeviceIds()` + `stop()` from code).

### SL2: two GATT servers on the peripheral phone expose the same service

nRF Connect was reopened on Phone B and its GATT server (Heart Rate, two other services and its own static copy of `12345678-...90ab`) ran next to the test app's server (`dumpsys bluetooth_manager`: Server app_if 6 nRF Connect, app_if 8 test app). The plugin subscribed to the first matching service, nRF Connect's static characteristic, so the counter stayed at 1. Fix: force-stop nRF Connect before every session (`adb shell am force-stop no.nordicsemi.android.mcp`) and check that only the test app is listed under "Server". Killing nRF Connect also dropped the link (status 19 on Phone A) because nRF Connect held its own client connection to Phone A.

### SL3: the phone peripheral's address changes after every advertising restart

After the link dropped at 11:58:28 (Phone B clock), Phone B re-enabled the same advertising set and appeared with a new private address (scan at 12:01: different address than the session's). Every reconnect then failed instantly with status 135 (autoConnect to an address that no longer exists). So with Phone B as peripheral, any test that needs a reconnect after a disconnect is setup-limited unless Phone A can resolve Phone B's rotating address (bonding) or a fixed-address peripheral is used. Evidence: 2026-10-14/S2-logcat.txt, 2026-10-14/S2-plugin-log.txt.

### SL4: an Android phone peripheral cannot drop a central-initiated link

`BluetoothGattServer.cancelConnection()` on Phone B (Android 13, One UI 5.1) did not end the link Phone A had opened, also not after `connect(device, false)` first. The `disconnect` command (checklist #6) therefore cannot be exercised with a phone peripheral; it needs the ESP32 or another peripheral that can terminate a link. Peer-initiated link loss was tested instead by switching Bluetooth off on Phone B (A3b).

### O3 (observation): link kept but peripheral app state lost after Bluetooth fully back on

After A3b, Phone B went from BLE_ON back to ON (12:44:51). Phone B's app reported the central disconnected and its advertising set stopped, but Phone A received no disconnect (no `onClientConnectionState`, no supervision timeout) and kept a link with no notifications. The plugin cannot distinguish this from a quiet peripheral. Not a plugin failure. Possible feature (not planned for 0.1): an optional "expected data interval" watchdog that reports or reconnects when a subscribed characteristic stays silent too long.
